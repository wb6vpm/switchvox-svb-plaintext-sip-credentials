# Technical Analysis

## Scope

CVE-2026-45362 affects Sangoma Switchvox On-Premise releases before 8.4. Testing reproduced the vulnerable backup behavior on versions 6.8, 7.9.5.2, and 8.3.

The vulnerability is not that Switchvox backups contain configuration data. A complete backup must contain configuration. The vulnerability is that affected backups can store active SIP authentication secrets in a directly readable archive without encryption.

Access to an affected `.svb` backup is required. Once the file is obtained, no further access to the PBX is needed to recover the carrier credentials.

## Affected Backup Format

Files generated by the tested releases used the `.svb` extension but began with this file signature:

```text
1f 8b 08
```

That is the gzip signature. Standard tools can list and extract the archive:

```bash
umask 077
mkdir extracted
gzip -dc backup.svb | tar -tf -
gzip -dc backup.svb | tar --no-same-owner --no-same-permissions -xf - -C extracted
```

Inspect an unfamiliar archive before extraction, and handle untrusted backups only in a disposable environment under a low-privilege account. The command above is intended for an authorized lab backup.

No Switchvox software, restore operation, backup password, or cryptographic work is required.

The extracted data places the backup package under `var/pbx_backups/backup_package/`. Representative contents include:

```text
var/pbx_backups/backup_package/
├── metadata.json
├── HST_PBX_CONFIG*.tar
├── MOH_FILES*.tar
├── PWE_VOICEMAIL_AND*.tar
├── XXX_SSL_CERTS*.tar
├── IAX_RSA_KEYS*.tar
├── ICE_SOUNDS*.tar
└── DUMP_MINUS_LOGS
```

`DUMP_MINUS_LOGS` is a plaintext PostgreSQL export containing the configuration needed to reconstruct the PBX.

## Credential Locations

The same SIP provider secret was observed in several records within `DUMP_MINUS_LOGS`:

| Record | Exposed material |
| --- | --- |
| `admin_activity_log` | Submitted provider password in administrative action parameters |
| `ps_auths` | SIP authentication username and password |
| `sip_providers` | Provider name, account, password, host, and related configuration |

### Synthetic test case

The following non-production values were entered through the Switchvox administrative interface:

| Field | Value |
| --- | --- |
| Provider name | `Test VoIP Provider` |
| Account ID | `example-account` |
| Password | `EXAMPLE-NOT-A-SECRET` |
| Provider host | `sip.example.invalid` |

The resulting backup contained entries equivalent to:

```text
submit_add_sip_provider
...
'provider_password' => 'EXAMPLE-NOT-A-SECRET'
```

```text
sip_provider_107    ...    password=EXAMPLE-NOT-A-SECRET    username=example-account
```

```text
107    Test VoIP Provider    example-account    EXAMPLE-NOT-A-SECRET    sip.example.invalid
```

This duplication is not required for exploitation, but it makes recovery of the live secret straightforward.

## Security Boundary

The exposed password is not merely historical configuration. It is the active credential that represents the PBX to the upstream carrier.

Authorized testing confirmed that credentials recovered from affected backups could authenticate against tested upstream SIP infrastructure. Depending on the carrier's authentication, source-IP restrictions, and registration model, a party using those credentials can appear to the carrier as the legitimate PBX.

The attack path is:

1. Obtain an affected `.svb` backup.
2. Extract the standard archive.
3. Read the SIP username, password, provider address, and related trunk settings from `DUMP_MINUS_LOGS`.
4. Where carrier controls permit it, authenticate from an attacker-controlled SIP endpoint.

Use of the credentials occurs directly between the external endpoint and the carrier. PBX firewalls, local SIP access lists, and PBX-side intrusion detection do not prevent carrier authentication after the secret has been recovered.

## Resulting Capabilities and Consequences

Unauthorized outbound call origination and toll fraud were observed in the production incident that led to this research.

Other capabilities depend on the carrier's configuration:

- caller identity abuse
- registration of an attacker-controlled endpoint
- inbound call interception or rerouting
- disruption from competing registrations

Fraud response can also produce operational consequences such as carrier blocking or account suspension. That consequence was observed in the production incident, but it is not described here as a technical capability granted by the credential.

The carrier-dependent qualification applies to the capabilities exposed after authentication. It does not apply to the plaintext credential recovery itself.

## Fixed Behavior

Sangoma lists Switchvox 8.4 as the patched version. Testing of 8.4 backups found that they were no longer directly readable as gzip/tar archives and instead began with a `Salted__` header, consistent with the encrypted backup handling described in the [Switchvox 8.4 release notes](https://sangomakb.atlassian.net/wiki/spaces/Switchvox/pages/1521647617).

The fix changes new backup handling. It cannot protect copies created before the upgrade or revoke credentials already recovered from them.

## Safe Reproduction

Testing should use a lab PBX, a synthetic SIP provider account, and carrier infrastructure owned by or explicitly authorized for the tester. Do not test recovered credentials against third-party carrier systems without permission.
